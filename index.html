Computer science student building toward SAP integration work

I am finishing a B.S. in Computer Science at Southern New Hampshire University, with a goal of becoming an SAP integration developer. I live in an area without a large technology industry, so I have steered my studies toward work that is realistically in demand near me: moving data between the systems a business already runs on, and making sure it arrives correct and protected.

How this program shaped my goals

When I started the program I planned to become a software developer. That changed when I was introduced to SAP, and then learned in one of my courses how data actually travels between systems. Integration work gave me a clear target. I am studying SAP Integration Suite on my own toward the SAP Certified Associate Integration Developer certification, and I have chosen my coursework and portfolio projects to build the skills that work depends on: keeping layers of a system separate, handling data carefully, and testing what I build.

The value I hold to most is that work should be checkable. In each of my three projects I tried to replace a guess with evidence, a measured benchmark in one and automated tests in the other two. An employer reading this portfolio can see the code before and after every change and check that the change did what I claim.

Working with others

I take part in a local community group of about fifteen members, where I help coordinate activities, communicate with members, and assist with technology when it is needed. When the group planned an event and members disagreed about the schedule and who was responsible for what, I collected everyone's suggestions, worked out who was available when, and proposed a schedule with clear assignments. The group agreed, and the event went ahead with everyone knowing their part.

The habits carry directly into technical teams: gather every point of view before arguing for one, find the real constraints, and turn a disagreement into a concrete plan with named owners. My examples so far come from outside software development, and I want to practice the same habits in code reviews and shared repositories.

Communicating with stakeholders

My clients in wedding photography and videography are couples who are not technical and are not shy about what they want. One couple asked for changes to their wedding film: more footage from the reception, smoother transitions, their vows laid over the music, different songs, and a stronger ending. I turned that feedback into a specific list of editing tasks, revised the film, and delivered a version that matched the moments and style they had in mind.

That is the same skill as turning a change request into requirements. In this program I applied it to writing: each narrative in this portfolio explains a technical change to a reader who did not write the code, in plain terms, with evidence.

Data structures and algorithms

My most direct algorithms work was in CS 370, where I built an agent that teaches itself to solve a maze. For this capstone I changed how it chooses which past experiences to learn from. Instead of reviewing them at random, it favors the ones it currently predicts worst. I chose that over a more complete version of the technique on purpose, because the full method needs an extra correction step and I could check the simpler change with a clear measurement. The agent reached a sustained 100% win rate in 280 training rounds instead of 484. What I take from this is the habit of choosing a data structure and an algorithm for a reason, naming the trade-off, and testing whether it paid off.

Software engineering and databases

In CS 360 I built an Android inventory app, and in CS 465 I built a full stack booking application with an Express and Node.js API, a MongoDB database, and an Angular admin site. Working on both taught me that most software problems are boundary problems: where the screen ends and the data begins, and where the API ends and the database begins. I now separate those layers on purpose, put the rules where the data lives, and write automated tests so I can change code with confidence. Those are the same habits integration work needs.

Security

I treat security as a design question, not a patch added at the end. In my database work I made the data layer reject malformed input, limited which fields a request is allowed to write, protected the delete operation behind login, and stopped the API from sending raw database errors to the client. I also follow developments such as the National Institute of Standards and Technology's post-quantum encryption standards, because the systems I want to connect will need to adopt them. Security is the outcome I consider only partly met so far, and the one I most want to keep building as I continue my SAP studies.

The three projects

Each project comes from a course earlier in the program and was improved in one of the three areas this capstone measures. Every page shows the narrative, a side-by-side comparison of the code before and after, and downloads of the original and enhanced files.

  • Software design and engineering: Android Inventory App

    The screens and the database were tangled together. I separated them with an MVVM design and Android Room, moved database writes off the main thread, and added automated tests of the data layer.

  • Algorithms and data structures: Pirate Intelligent Agent

    A learning agent that studied its past moves in random order. I changed it to review the moves it was getting most wrong, and it reached a 100% win rate after 280 training rounds instead of 484.

  • Databases: Travlr Getaways

    A booking API that accepted almost any data and could not delete a trip. The database layer now enforces its own rules, protects deletion behind login, and keeps internal errors private, backed by 33 automated tests.

How the projects fit together

The three projects look different, but they share one idea: data moves through layers, and each layer has a job to do correctly. In the Android app, that meant keeping what the user sees apart from where the data is stored, so each can change and be tested without breaking the other. In the Pirate Agent, it meant improving which data the algorithm studies, and proving the change helped with a measurement instead of an assumption. In Travlr Getaways, it meant making the data layer defend itself, so that bad input is rejected where the data lives no matter which route or script sends it.

That is also the core of integration work. A connection between two systems is only useful if the data that crosses it is well formed, the failure cases are handled safely, and someone has tested it. Each narrative explains what I changed, which course outcomes the work meets, and where I fell short of full coverage.

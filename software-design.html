Narrative

Artifact Description

The artifact for this milestone is the Android Inventory Management App, originally developed for CS 360: Mobile Architecture and Programming. The application allows an authenticated user to log in, view a list of inventory items, add new items, increase or decrease an item's quantity, delete items, and receive an SMS alert when an item's quantity reaches zero. In its original form, the app stored data using a single DatabaseHelper class that extended SQLiteOpenHelper directly, managing two unrelated tables, a users table for login credentials and an items table for inventory records, through hand-written SQL strings and ContentValues objects. Every database call, including inserts, updates, and deletes, executed synchronously on the UI thread inside the Activity classes themselves, with no separation between the app's data layer and its screens.

Justification and Description of Enhancement

I selected this artifact because it already existed in a working state in my GitHub repository and because its data layer was the clearest demonstration opportunity for the software design and engineering outcomes this course targets. The original implementation worked, but it mixed data access directly into the UI layer, offered no automated tests, and performed all database operations on the main thread, a pattern that risks unresponsive UI behavior under load even though it was not noticeable in a small local SQLite file.

The enhancement refactored the inventory portion of the app into an MVVM architecture using the Android Room persistence library. I converted the InventoryItem class into a Room @Entity, replaced the item-related methods in DatabaseHelper with an InventoryDao interface using Room's @Insert, @Update, @Delete, and @Query annotations, and added an AppDatabase class to manage the Room instance as a singleton. I then built an InventoryRepository that routes every write operation through a background ExecutorService rather than the UI thread, and an InventoryViewModel that exposes the item list as LiveData. InventoryActivity and AddItemActivity no longer instantiate DatabaseHelper directly; they now request an InventoryViewModel and observe its LiveData, so the on-screen list refreshes automatically whenever the underlying data changes, instead of relying on a manual reload in onResume(). I intentionally left the users table and its login methods (checkLogin, usernameExists, addUser) on the original DatabaseHelper, since the login flow was outside the scope of the enhancement plan established in Module One; converting it would have been scope creep without a corresponding outcome to demonstrate. Because both the legacy DatabaseHelper and the new Room database could not safely share the same underlying database file, I also renamed the Room database file and incremented DatabaseHelper's schema version so that any device with the app already installed cleanly drops the now-unused items table from the login database on upgrade, rather than leaving orphaned data behind. Finally, I added three instrumented unit tests in InventoryDaoTest, run against an in-memory Room database, that verify inserting an item, updating its quantity, and deleting it by ID all behave correctly independent of the UI.

Course Outcomes

This enhancement meets the course outcomes I identified for this artifact in Module One. Outcome 4 asked me to demonstrate an ability to use well-founded, innovative techniques and tools in computing practice to deliver value and accomplish industry-specific goals; the shift from a single hand-rolled SQLiteOpenHelper class to Room's Entity/DAO/Repository/ViewModel structure, background-threaded writes, and reactive LiveData-driven UI updates reflects current, widely used Android architecture practice rather than the original ad hoc approach, and the addition of automated tests provides verifiable evidence that the refactor behaves correctly rather than relying on manual observation alone. Outcome 2 asked me to design, develop, and deliver professional-quality communications that are coherent, technically sound, and adapted to their audience; this narrative itself, along with the inline documentation I kept in each new class explaining why the repository moves writes to a background thread and why the users table was intentionally left out of the Room migration, are the concrete evidence for that outcome, since they translate the technical reasoning behind the refactor into a form a reader who did not write the code can actually follow. I do not have any changes to report to the original enhancement plan; the refactor was completed largely as planned in Module One, with the addition of unit tests, which was part of the original plan's intent but had not yet been implemented at the time of that first draft.

Reflection

The most useful thing I learned in this milestone was how much a change in architecture changes the shape of bugs you have to worry about. The original code's bugs, if any, would have been visible immediately, since every operation ran synchronously and any failure showed up as a return value you could check right there in the click listener. Moving inserts, updates, and deletes onto a background thread through the repository removed that immediate feedback; I had to give up the old "if the insert succeeded, show a success toast, otherwise show an error toast" pattern in AddItemActivity, since the write no longer completes before the method returns. That is a real trade-off worth naming honestly: I gained thread safety and a UI that cannot freeze on a slow write, but the app now assumes writes succeed rather than confirming it synchronously, which would be worth revisiting with a callback or a LiveData-wrapped result in a future iteration.

The most concrete mistake I had to catch and fix during this milestone was pointing the new Room database at the exact same file name the legacy DatabaseHelper already used for the login table. Room and a hand-written SQLiteOpenHelper cannot safely manage the same physical database file with two different schemas, and catching this before running the app, rather than after seeing a confusing runtime crash, reinforced how much architectural decisions in one file can have consequences in a completely different, seemingly unrelated file. Renaming the Room database file and bumping the legacy helper's schema version resolved it, but it was a reminder to think about the full set of files touching persistence, not just the ones being actively rewritten. Writing the instrumented DAO tests afterward was valuable for a similar reason: rather than trusting that the refactored insert, update, and delete logic worked because the emulator's UI looked correct, the tests gave me an independent, repeatable way to confirm that the DAO itself behaves correctly against a real, if temporary, database.

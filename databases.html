Narrative

Artifact Description

The artifact for this milestone is Travlr Getaways, a full stack travel booking application I built in CS 465 in 2026. It has an Express and Node.js back end with a REST API, a MongoDB database accessed through Mongoose, a server-rendered customer website built with Handlebars, and an Angular single page application that staff use to manage trips. The API stores trips in a trips collection, exposes that data to both front ends, and protects the routes that change data with JSON Web Token authentication through Passport. The part of the artifact I enhanced is the database layer: the Mongoose trip model, the trip controller, and the API routes that read and write it.

Justification and Description of Enhancement

I chose this artifact because it is the strongest example of my database work. It is the one project where I designed a schema, connected an application to a real database, and exposed that data through an authenticated API, and my Module Two code review showed exactly where the data layer was weak. The original trip model only required each field to be present, so a trip could be saved with a one-character code, a price that was not a price, or an image value containing markup. The trip code, which every single-trip route uses to find a record, was indexed but not unique, so two trips could share a code. Updates skipped validation entirely, because Mongoose does not run schema validators on findOneAndUpdate unless it is told to. The API also had no way to delete a trip, and when something failed it sent the raw database error back to the client.

The enhancement addressed each of those problems. I added schema-level validation to every field of the trip model, including trimmed text, length limits, a price format, a restricted format for trip codes, and a path-or-URL format for images, and I made the trip code a unique index. I turned on validators for updates so the same rules protect edits. I added a DELETE route and controller, protected by the same JWT authentication as creating and updating a trip. I changed the controller so it only reads the eight expected fields from a request and leaves fields the client did not send untouched, and I replaced the raw error responses with specific messages for validation failures (400), duplicate codes (409), and missing trips (404), plus a generic message for anything unexpected, with the details logged on the server only. I also fixed the single-trip lookup so it returns 404 for an unknown code instead of an empty list with a success status.

An existing database already has a non-unique index on the trip code, and MongoDB will not change an index's options in place, so marking the code unique in the schema alone would not have taken effect on a database that already existed. I therefore added a step to the database connection that synchronizes the indexes with the schema when the application connects. I have not yet run that step against a live database, so it is the one part of this enhancement that I verified by design and code review rather than by running it.

I verified the rest with 33 automated tests that run without a database. They cover the validation rules, the unique index declaration, each controller response, and the route configuration, including that DELETE sits behind authentication in the same way as POST and PUT. One test runs every trip in the project's existing data file through the new schema, which confirmed that the stricter rules do not reject data the application already has. All 33 tests pass.

Course Outcomes

This enhancement meets the outcomes I planned for it. Outcome 4 asked me to use well-founded techniques, skills, and tools to implement a solution that delivers value; schema validation, a unique index, validators on updates, and a protected delete operation are standard practice for a database-backed API, and the automated tests give verifiable evidence that they work rather than relying on manual checking. Outcome 5 asked me to develop a security mindset that anticipates adversarial exploits and protects the privacy and security of data. The enhancement does that by rejecting malformed input at the data layer, including operator-like strings in the trip code, by restricting which fields a request can write, by keeping internal database details out of error responses, and by putting the new delete operation behind the same authentication as the other write routes. I consider this substantial progress on Outcome 5 rather than full coverage. One limit I want to note is that the description field is restricted by length but not by content, so if descriptions are ever displayed as unescaped markup, sanitizing them would be a further step that I would take in the final version.

I do have updates to report on my plan. The plan from my Module Two code review was to add the missing DELETE endpoint and schema-level validation, and I completed both. I added several changes beyond that plan, namely the unique index, validators on updates, field restriction, safer error responses, and the 404 fix, because reviewing the full path a request takes showed that validation alone would still leave updates and error responses unprotected. The original code already declared indexes on the trip code and name, so instead of adding new indexes I made the existing code index unique, which was the change that mattered for correctness.

Reflection

The most useful thing I learned was that validation has to live where the data lives. Checking input in the Angular form helps users, but the API accepts requests from anywhere, so the only dependable place to enforce the rules is the schema and the code that writes to it. I also learned how many separate paths lead into the same collection. Creating, updating, and now deleting each needed their own attention, and the update path was the easy one to miss, because Mongoose skips validators on updates by default.

The main challenge was making the rules stricter without breaking data that already existed. A pattern that is too strict would have rejected trips the application already had, and a new unique index can fail against a database that already contains duplicates. I handled the first by running the existing trip data through the new schema in an automated test before trusting the rules, and the second by making the index step log a clear message and let the application keep running rather than fail to start. Working through the existing index taught me a related lesson, that a change to a schema file does not automatically change a database that already exists. Writing the tests also surfaced a bug in the original code that I had not noticed before, which was that the single-trip lookup could never return a 404, and that reinforced for me how much a test suite can reveal about code that appears to work.
